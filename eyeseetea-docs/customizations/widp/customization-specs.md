## Known WIDP customizations

### 1. Server URL change by user

Status:
- `active`

Functional intent:
- Field users need to switch between different DHIS2 server instances from within the app without reinstalling or reconfiguring.

Expected behavior:
- The settings screen includes an option to change the server URL.
- The app validates the new URL before applying.
- The user is re-authenticated after the server URL changes.
- The previous server URL is no longer used for API calls.

### 2. Image upload without resizing

Status:
- `active`

Functional intent:
- Clinical and field photos must preserve original quality and resolution for diagnostic or documentation purposes.

Expected behavior:
- Image capture and upload flows do not apply client-side compression or resizing.
- The full-resolution image is sent to the server.
- This behavior applies regardless of image source (camera or gallery).

### 3. Notifications system

Status:
- `active`

Functional intent:
- The app reads notifications from the DHIS2 datastore (`dataStore/notifications/notifications`), filters them for the current user, stores them locally and displays them on app load. Notifications support multiple languages. When the user accepts a notification it is marked as read and synced back to the server.

Data source:
- Server endpoint: `dataStore/notifications/notifications` (GET to read, PUT to update).
- Each notification contains: `id`, `content`, `translations`, `recipients`, `readBy`.

Sync flow:
- During metadata sync the app fetches all notifications from the datastore.
- It also fetches the current user's group memberships via `users/{userId}?fields=userGroups`.
- Notifications are filtered for the current user (see filtering rules below).
- Only the filtered notifications are saved to SharedPreferences (`NOTIFICATIONS` key).

Filtering rules — a notification is for the current user when:
1. It has NOT already been read by this user (the user's ID is not in `readBy`).
2. AND at least one of these recipient conditions is true:
   - **Wildcard = "ALL"** (case-insensitive): broadcast to every user on every platform.
   - **User group match**: at least one of the notification's `recipients.userGroups` matches one of the user's groups, AND the notification targets Android (wildcard is "Android", "Both", or empty).
   - **Direct user match**: the user's ID is in `recipients.users`, AND the notification targets Android (wildcard is "Android", "Both", or empty).

Platform targeting (`isForAndroid`):
- Accepted values for wildcard: `"Android"`, `"Both"`, `""` (empty), `"ALL"` (any case).
- Rejected: `"Web"` or any other value.

Display:
- On activity resume the presenter loads notifications from SharedPreferences.
- Each notification is shown in a Material AlertDialog.
- The content supports Markdown rendering (via Markwon).

Translation handling:
- Each notification has a `translations: Map<String, String>?` field (key = language code, value = translated content).
- The app resolves the device locale via `Locale.getDefault().getLanguage()`.
- If a translation exists for the locale, it is used; otherwise the default `content` field is displayed.

Mark as read:
- The user clicks the OK/Accept button on the dialog.
- A `ReadBy` entry is created with the current user ID, display name and timestamp.
- The entry is appended to the notification's `readBy` list.
- The full notification list (with the updated `readBy`) is PUT back to the datastore endpoint.
- Once marked as read the notification will no longer appear for that user (filtered out by the readBy check).

### 4. 2FA support

Status:
- `active`

Functional intent:
- The official DHIS2 SDK only supports TOTP-based 2FA. This customization extends the login flow to support three 2FA types: **TOTP**, **Email** and **SMS**, using an EyeSeeTea-patched SDK. It also adds a resend mechanism for email/SMS codes and rate-limiting detection.

Supported 2FA types:
- **TOTP** (Time-based One-Time Password): the user enters a code generated by an authenticator app.
- **Email**: the server sends a verification code to the user's email. The app shows a "Resend Email Code" button (disabled 30s after each resend).
- **SMS**: the server sends a verification code via SMS. The app shows a "Resend SMS Code" button (disabled 30s after each resend).

Authentication flow:
1. The user enters username and password and clicks login.
2. The SDK calls `blockingLogIn(username, password, serverUrl, twoFactorCode)`.
3. If the server requires 2FA, the SDK returns a specific D2ErrorCode depending on the type.
4. The app detects the 2FA type from the error code and shows the corresponding input field:
   - TOTP: a text field labeled "TOTP Code".
   - Email: a text field labeled "Email Verification Code" + resend button.
   - SMS: a text field labeled "SMS Verification Code" + resend button.
5. For Email/SMS, the first response from the server is informational ("code sent"), shown as a blue info message.
6. The user enters the code and clicks login again. The SDK re-calls `blockingLogIn` with the `twoFactorCode` parameter.
7. On success the login proceeds. On incorrect code the field shows a red error message.

Resend mechanism (Email/SMS only):
- Clicking "Resend" calls login again without a `twoFactorCode` (null), which triggers the server to send a new code.
- The resend button is disabled for 30 seconds after each attempt.
- If too many resend attempts are made, the server returns `TWO_FACTOR_MANY_SEND_ATTEMPTS` and the app shows "Many send attempts. Contact your system administrator."

SDK patch (what it adds vs official SDK):
- `LoginPayload` includes an optional `twoFactorCode: String?` parameter.
- `LogInCall.generate2FAErrorIfRequired()` parses 2FA-specific status codes from the server response (DHIS2 v2.42+).
- New D2ErrorCode values: `EMAIL_TWO_FACTOR_CODE_SENT`, `INCORRECT_TWO_FACTOR_CODE_EMAIL`, `SMS_TWO_FACTOR_CODE_SENT`, `INCORRECT_TWO_FACTOR_CODE_SMS`, `TWO_FACTOR_MANY_SEND_ATTEMPTS`.

Error messages:
- TOTP incorrect: "Incorrect two factor code"
- Email code sent: "Email with two factor code sent"
- Email incorrect: "Incorrect authentication code"
- SMS code sent: "SMS with two factor code sent" (note: current string may contain a typo showing "Email" instead of "SMS")
- SMS incorrect: "Incorrect authentication code"
- Too many attempts: "Many send attempts. Contact your system administrator."

### 5. URL data element field

Status:
- `broken` — plumbing exists but rendering was lost in an upstream refactor

Functional intent:
- Data elements can have a `url` property configured on the server. When a data element has a URL, that URL should be shown to the user alongside the field description so they can access reference material (e.g. clinical guidelines, SOPs) directly from the form.

Original implementation (commit `c556b7ab7`, Nov 2022):
- `EventRepository` reads `de?.url()` from the SDK data element and passes it through `fieldFactory.create(..., url = url)`.
- `FieldUiModel` interface has a `val url: String?` property.
- `FieldUiModelImpl` stores it and in `onDescriptionClick()` concatenated the URL to the description:
  ```kotlin
  if (url == null) description else description + "\n" + url
  ```
- When the user tapped the info/description icon on a field, a dialog showed the description + URL.

Current state:
- The data plumbing is intact: `EventRepository.kt` reads the URL, `FieldUiModel.kt` declares the field, `FieldUiModelImpl.kt` stores it, `FieldViewModelFactoryImpl.kt` passes it through.
- `EnrollmentRepository.kt` passes `url = null` everywhere (URL only applies to event data elements).
- The rendering is **lost**: the old `onDescriptionClick()` method and `RecyclerViewUiEvents.ShowDescriptionLabelDialog` were removed during the upstream migration to Compose. The URL value is stored in the model but never displayed.

Action required:
- Reimplement the URL concatenation to description in the new Compose-based form UI.
- Find where the description/info icon dialog is now rendered and add the URL there.

## Maintenance rule

When a customization is confirmed to still exist after an upgrade:
- keep its functional meaning here
- keep its file-level implementation in `customization-files.md`
- keep its minimal manual validation in `eyeseetea-docs/upgrade/widp/upgrade-validation-checklist.md`

When a customization is removed or absorbed by the base branch:
- update the status here explicitly
- do not leave obsolete functional specs as if they were still active
